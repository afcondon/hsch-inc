## Accomplished

### link-spike binary (new project)
- Stand-alone Rust binary at `purescript-ports/purerl-tidal/link-spike/`, sibling to `cv-router/`
- Uses [`rusty_link`](https://crates.io/crates/rusty_link) — Rust FFI wrapper around Ableton's official C++ Link library (`abl_link` extension)
- Joins a Link session, polls the shared timeline at 1ms granularity, fires OSC `/cv/trig <bus> 0.5 <ms>` to cv-router on each integer beat
- Pulse width derived from live tempo on each fire: `60_000 / bpm * duty` ms, default 50% duty
- CLI: `link-spike [bus] [duty]`; defaults to bus 8 (= ES-9 panel jack 1) and 0.5 duty
- ~90 LOC; clean build first try (~28s including C++ Link compile)
- Marginalia project 186 (sierra-lima-yankee-charlie), child of project 90 (purerl-tidal)

## Explored But Not Pursued

### Pure-Rust Link reimplementation
Considered briefly, rejected immediately. Link's clock-sync algorithm is subtle and Ableton's C++ has had years of real-world bake-in across Live, hundreds of iOS apps, and hardware modules like the ML-2. Reproducing bug-for-bug is a yak. FFI to vendored C++ is the right call.

### Sample-accurate scheduling
The current "fire OSC immediately on detecting the beat boundary" introduces:
1. cv-router's audio buffer latency (~8 ms at 32 kHz / 256-frame buffers)
2. link-spike's 1 ms polling jitter
3. OSC encode + UDP loopback (sub-ms)

The principled fix is to use Link's `time_at_beat` to compute the *absolute* future time of each beat, encode that into the OSC message (`/cv/trig/at <bus> <val> <dur_ms> <abs_micros>`), and have cv-router schedule the gate trigger to fire at exactly that audio frame inside the audio callback. Deferred — the current jitter is musically usable for the spike, and the work to do it right is its own slot.

### "Modes switch" in ES-9 to monitor phones
Andrew flagged a mode-toggle on the ES-9 that would route phones to monitor mode but feared it would mess our config. We confirmed (via dumping the matrix) that the routing change he needed was a small in-place edit, not a mode toggle.

## Phase 2.5 — typed PureScript model of ES-9 config (started this morning)

After the Phase 2.6 writeup we kept going. By lunch we had stages 1-3 of Phase 2.5 in the bag.

### Decision: location
Settled on `purerl-tidal/es9-config/` (sibling to cv-router and link-spike, ab inicio under the purerl-tidal umbrella) rather than `music/es9-config-ps/`. The umbrella framing is "ES-9 suite" — config + audio router + Link client co-located.

### Decision: imperative-PoC-first via vendored midi.js
Andrew's call: rather than reverse-engineering the SysEx protocol from scratch, vendor Andrew Os' midi.js (Expert Sleepers, MIT licensed) as the imperative bottom layer and lift PureScript types over the top. Faster to working product, lower risk of misunderstanding the protocol, and respects that Os has already paid the cost of figuring out the byte-level details. He told Andrew years ago via email that hacking on it was welcome — combined with the explicit MIT license, copying with attribution is fine. Lives at `es9-config/src/ES9/MIDI.js` with a header pointer at the upstream.

### Stage 1 — Spago skeleton (✅)
Modern packageSet (`registry: 76.1.1`), `type: module` package.json, FFI conventions (.js alongside .purs with same name). Build green first try.

### Stage 2 — typed ADTs + decode-from-Foreign (✅)
Three modules:
- `ES9.Types` — `Source`/`Destination` ADTs with paired `fromCode`/`toCode` functions. Hides the wire-encoding pivot-tables: panel-out internal numbering (`8/9/4/5/2/3/11/10` → user-order `1..8`) and the `inputCaptureLookup` remap. The user space is `Input 1..14`, `USB 1..16`, `Out 1..8`, `Main L/R`, `Phones L/R`, `ES-5 L/R`, `Bus 1..16`, `S/PDIF L/R`.
- `ES9.Decode` — thin FFI extraction from midi.js's parsed JS object into typed `Config`. No codec library: the shape is fully known and stable, so simple `readVersion` / `readRouteIn` / `readRouteOut` JS shims suffice. Codec library would be overkill for a stable, decoded-once boundary.
- `ES9.Pretty` — typed Config → readable text per DSP block, `ch N: Source → Destination`.

End-to-end output for the captured flash-state dump (32 lines of obvious text where the Electron pivot table needed clicking through 4 DSPs × 8 channels × 2 sub-tables to read).

### Stage 3 — DSL parser + symmetric printer (✅)
- `ES9.Parser` — `purescript-parsing` combinators, accepts both `→` and `->` arrows, whitespace-tolerant. Same shape Pretty produces, so a `.es9` file written by hand is parseable too.
- Round-trip property holds: `parse(print(decode(bytes))) == decode(bytes)`.

## Stage 3.5 — full binary round-trip (✅ pre-lunch)

`ES9.Encode` patches the routeIn/routeOut byte ranges of a copy of the original SysEx, applying the inputCaptureLookup remap in reverse. Crucially: only patches the bytes we've modelled — version, mixer levels, options, etc. round-trip unchanged because we keep the original bytes as base.

Round-trip property `encode(decode(bytes)) == bytes` holds (all 2313 bytes match) on the captured fixture. So the full pyramid is now closed:

```
binary bytes  ←→  typed Config  ←→  DSL text
     2313 B          slots             32 lines
```

All three representations interconvert losslessly.

## Stage 4 — live MIDI read (✅)

`@julusian/midi` (Node binding to rtmidi) for MIDI I/O. Three FFI primitives: `newInput`/`newOutput`, port enumeration + open/close, and `sendSysEx` + a one-shot `onceConfigDump` listener. Async layer is `Effect.Aff` via `makeAff`.

CLI surface in `Main.purs`:
- `spago run` — fixture mode (offline, deterministic)
- `spago run -- --list-ports` — enumerate Mac MIDI ports
- `spago run -- --live` — request config from the actual ES-9, decode, print as DSL
- `spago run -- --live-loopback` — live read, write back unchanged, verify

Worked first try once the `ignoreTypes(false, true, true)` call was in (rtmidi defaults to ignoring SysEx). 2313 bytes live-read off the device, full round-trip green.

## Stage 4.5 — live MIDI write (✅)

ES-9 doesn't accept the `0x08` config-dump format as a write — that's request-reply only. Writes use targeted update messages: `0x40+dsp` for input routing, `0x50+dsp` for output routing, `0x60+mix` for mixer gains, etc. Each carries 8 single-byte values for the 8 channels of one DSP.

Implementation: `sendUpdateInputRouting` and `sendUpdateOutputRouting` in `ES9.Live`, plus a `writeRouting :: Output -> RoutingMatrix -> Aff Unit` driver in `Main` that loops over the 4 DSPs, slicing the encoded routing into per-DSP chunks and sending both messages with a 30 ms gap between each pair.

Acceptance test (`--live-loopback`): read current config, write it back unchanged via update messages, re-read, compare. Result:

- ✓ typed Config identical before and after
- ✓ raw bytes identical before and after

Meaning the encoder produces wire-format that the device round-trips bit-for-bit. Editing the DSL, parsing, and pushing changes is now a closed loop.

## Decisions (Phase 2.5)

- **Stay imperative-PoC-first via vendored midi.js** rather than reverse-engineering the SysEx protocol. midi.js is MIT-licensed, Os' work, ~470 lines, vendored at `es9-config/src/ES9/MIDI.js` with attribution header. PureScript wrappers sit on top.
- **Skip codec library for the JS-Foreign boundary**. The shape of midi.js's parsed config object is fully known and stable; simple FFI extraction (`readVersion`, `readRouteIn`, `readRouteOut`) suffices. A codec library (e.g. argonaut) would be overkill for a stable, decoded-once boundary. Revisit if the structure proves less stable than expected.
- **`purescript-parsing` for the DSL parser**, not hand-rolled. Combinator-style parser is cleaner and the round-trip property is the principled-correctness check.
- **Patch-only-what-we-modelled binary encoder**. Instead of having to encode the entire 768-word config to round-trip, we keep the original bytes and overwrite just the routeIn/routeOut byte ranges. This means partial typed coverage doesn't block the full round-trip — every config field we haven't typed yet just passes through unchanged.
- **Two-binary live MIDI** via `@julusian/midi` (Node FFI) rather than Web MIDI. Headless tooling fits the "single script launch" thesis better than a browser app for now; Web MIDI is still on the table for a future Halogen UI.
- **`--live-loopback` as the acceptance test for writes** instead of editing real state. Idempotent no-op write is the safest possible proof of the encoder, and any encoder bug shows up as a `before != after` mismatch rather than as a corrupted device config.

## Parking Lot (Phase 2.5+)

- **Sugar layer** for the DSL — Andrew's original sketch (`USB 1..2 → Main L, R`, range and fanout on RHS). Becomes syntactic sugar over the slot grammar; needs a slot-allocator to decide which DSP/channel each desugared slot lands in. Worth thinking about explicitly before designing it.
- **Other config sections** beyond routing — mixer levels (16 mixers × 8 channels of 21-bit gain), stereoLinks, options word (S/PDIF vs Mixer 2), DC blocking, MIDI channels, output DC offsets, filters, smoothing. Each is a small typed-model extension following the routing template; the live-write side has analogous `0x60+mix` etc. update messages.
- **`.es9` file format** — pretty-printer output saved as a textual artifact, parser reads it back. Makes config-as-code real (versionable, diffable, code-reviewable). Trivial given parse + print are already there.
- **Halogen UI** atop the same typed model — visual signal-flow editor, but with the typed model as ground truth and the DSL as the export/import format. Far future.
- **save-to-flash command** — currently all writes are volatile. Add a `--save-to-flash` flag that issues `0x24` after the routing writes.

### Phase 2.7 — first sound on the modular

Goal: get Tidal patterns playing music on Rample (samples), Plaits (pitched/melodic), Cursus Iteritas Percido (wavetable). Started the afternoon with the question "why does `bd sn hh cp` produce only `ch 0` triggers?"

**Root cause**: `Tidal.WebSocket.Handler` always sends `UpdatePattern` (legacy single-channel path) even though the scheduler supports `UpdateTracks` with per-track channels. Default config has `channel = 1, channelOffset = 9` so the gate-channel arithmetic `1 - 10 + 9 = 0` lands every event on cv-router ch 0 regardless of sample name.

**Fix #1 — sample-name fanout** (small, in-scheduler):

Added `sampleGateMap :: Map String Int` to `GateConfig` plus a `defaultSampleGateMap` covering the GM-drum aliases (`bd→0, sn→1, hh→2, cp→3, rim→4, lt/tom/mt→5, ht→6, cy/crash/rd/ride→7`). Tick handler looks up by sample name first, falls back to the old per-track-channel arithmetic. `bd sn hh cp` now correctly fans out across 4 cv-router channels with no protocol change.

**Fix #2 — BEAM-side delayed gate sends** (correctness fix):

After fanout worked, listening revealed all gates firing simultaneously regardless of pattern position. Diagnosis: `OSC.sendGateTrig` had no delay parameter, so the scheduler's 100ms-lookahead burst sent all events for the next cycle as a tight succession of OSC messages. cv-router's `set_target+set_deadline` then collapsed overlapping same-channel triggers into a single extended pulse.

First attempt — switch to the new `/cv/trig/at` verb — exposed a different bug: cv-router keeps a *single* `pending_start[ch]` slot per channel. With 8 events for `hh*8` arriving in <1ms, later `schedule_trigger` calls clobber earlier ones before the audio callback can apply them. Only the latest scheduled trigger per channel per sweep actually fires. Visible flashes, missed Rample triggers.

Final fix: `OSC.sendGateTrigAfter` mirrors the MIDI side's `spawn(fun() -> timer:sleep(DelayMs), ... end)` pattern — each event arrives at cv-router as a standalone `/tidal/gate/trig` at the moment it should fire, so `set_target+set_deadline` works correctly and there's no per-channel collision. Trades sample-accuracy (~one audio buffer of jitter) for correctness with overlapping events. The `/cv/trig/at` verb is kept for callers that guarantee at most one in-flight trigger per channel (link-spike).

**Fix #3 — cv-router GATE_CHANNELS 4 → 8**:

cv-router was silently dropping `/tidal/gate/trig` for `ch >= 4` because the original design treated jacks 1-4 as gates and jacks 5-8 as CVs. With our scheme using all 8 panel jacks freely as gates (`bd→0` through `ride→7`), Plaits trigger on jack 7 (ch 6) was being silently rejected. Bumped to 8. The `/tidal/cv` verb still maps to bus 12-15 for backward compat.

### Phase 2.7 evening — pitched CV for Plaits (V/oct)

Andrew patched ES-9 jack 7 → Plaits trigger (gate ch 6 = bus 14) and jack 8 → Plaits V/oct (bus 15). Goal: drive Plaits melodically from a Tidal pattern by pre-setting V/oct just before each trigger.

Key observation: cv-router's `/cv` direct-bus verb doesn't apply `SAFETY_SCALE` (only `/tidal/cv` does), so V/oct can hit the full ±10V range. ES-9 maps digital ±1.0 → ±10V, giving `value = midiNote / 120.0` for standard 1V/octave (MIDI 60 = C4 = digital 0.5 = 5V).

**Implementation** (purely PureScript-side, no cv-router changes needed):

- New OSC FFI `sendCVAfter :: OSCClient -> Int -> Number -> Number -> Effect Unit` mirroring `sendGateTrigAfter`. Spawns BEAM process, sleeps `delay_ms`, sends `/cv <bus> <value>`. Different verb, otherwise identical pattern.
- Extended `GateConfig` with `sampleCVMap :: Map String { bus :: Int, value :: Number }` and `cvLeadMs :: Number` (default 5.0 — V/oct settle margin).
- `defaultSampleCVMap` covers C3..C6 (37 note names) all mapped to bus 15.
- `defaultSampleGateMap` extended with the same note names → gate ch 6 (Plaits trigger). So a token like `c4` triggers BOTH a CV update on bus 15 AND a gate pulse on ch 6.
- `voctValue :: Int -> Number` and `noteEntry :: String -> Int -> Int -> Tuple String { bus :: Int, value :: Number }` exported as helpers for callers that want to wire other pitched-voice modules.
- Scheduler tick handler: looks up `sampleCVMap` first, fires `sendCVAfter osc bus value (delayMs - cvLeadMs)`, then fires the gate trigger as before.

**False alarm during testing**: After the first `c4 e4 g4 c5` test, cv-router's log appeared empty — but that was Rust's block-buffered stderr when redirected to a file. Forcing the buffer to flush (subsequent unrelated traffic) revealed cv-router HAD logged 42 `direct bus 15 = ...` lines, perfectly alternating with `gate/trig ch 6` entries. Lesson: don't trust an empty `tail -n` of a redirected Rust binary's log without giving it a few seconds (or piping through `stdbuf -o0`).

**Acceptance**: 4-layer stacked pattern `[bd ~ bd ~, ~ sn ~ sn, hh*8, c4 ~ e4 ~ g4 ~ c5 ~]` produces:

- 7 snares (ch 1)
- 29 hi-hats (ch 2)
- 28 Plaits triggers (ch 6) paired 1:1 with 28 V/oct updates (bus 15)
