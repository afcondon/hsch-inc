# 2026-04-26 — ES-9 configurator + per-track gate/CV patterns

## Accomplished

### Morning: ES-9 configurator extensions

Power-cycle exposed the Phase 2.5 worklog parking lot: ES-9 routing was
volatile, no save-to-flash, no DSL-driven setup. Closed those gaps.

**`--live-set-cv-router`** — single CLI command writes a known-good
config:

- DSP 2: `USB 1-4 → Main/Phones`, `USB 9-12 → Out 1-4`. Modified to
  route `Input 1/2 → Phones L/R` so panel inputs are monitored through
  ES-9 headphones (DSP 2's 8 slots are the inputs to Mix 3/4 = Phones).
- DSP 3: `USB 13-16 → Out 5-8`, four muted slots with `Bus 1` source
  (so the mixer view doesn't show duplicate USB labels).
- DSP 1: muted entirely (was passing expander inputs + S/PDIF onto our
  panel outs at unity gain, adding low-level noise).
- DSP 0: preserved (panel inputs → ES-5 expander L/R).

Routing wire codes hidden behind a typed model: `SrcUsb`, `SrcInput`,
`DstMainL`, `DstPanelOut`, etc. (`ES9.Types`).

**Mixer state** — `--live-read-mix` reads the 16×8 gain matrix
(separate `0x2A`/`0x11` SysEx, NOT in the config dump). Convention
deduced empirically:

- Mix 1-4 = Main L, Main R, Phones L, Phones R
- Mix 5-12 = Out 1-8
- For routing slot `(DSP_idx, slot_idx)` driving destination D, set
  `Mixer(D)` channel `slot_idx` to unity (8192). Formula matches the
  Electron app's `mixBus = (dsp - 2) * 8 + ch` for DSP 2/3.

**Save to flash**: `0x24, [slot]`. ES-9 has two slots:

- slot 0 = Standalone (used when ES-9 boots without USB host)
- slot 1 = Hosted    (used when ES-9 sees USB at boot)

`--live-save-to-flash` defaults to slot 1 (Hosted, what we want for
cv-router workflow). `--live-save-to-flash-standalone` for the rare
rack-only persona.

**`--live-set-cv-router` now also writes mixer entries** for our routing,
clearing all 128 mixer channels first so stale settings don't linger.
End-to-end: read current → modify typed model → encode → write routing
+ clear mixer + write mixer entries → re-read → verify.

### Afternoon: per-track gate/CV patterns

Phase 2.7 follow-on, motivated by Andrew wanting Tidal-idiomatic
patterned LFOs for Plaits modulation (and Rample sample-select layers).

**Gate/CV prefix protocol** on the WebSocket:

```
gate <ch> <pattern>    # set gate track on channel, leave others
cv   <bus> <pattern>   # set CV track on bus; numeric tokens
<plain pattern>        # legacy single-track-replace-all
```

Gotcha that cost an hour: WS dispatch is hand-written in
`Handler.erl`, not the PureScript `Handler.purs`. Adding prefix parsing
to `parseInputMessage` in PureScript was a no-op — purs-backend-erl
tree-shook the unused functions. The actual dispatch is in
`tidal_webSocket_handler@foreign.erl`'s `websocket_handle` callback,
which calls `parse_message` and forwards `{updatePattern, ...}` to the
scheduler. Added `try_parse_prefixed/1` in the .erl directly, sending
`{updateGateTrack, Ch, Pat}` / `{updateCVTrack, Bus, Pat}` to the
scheduler (matches the Erlang encoding of the new ADT constructors).

**Scheduler refactor**: `ParsedTrack` is now a sum:

```purescript
data ParsedTrack
  = GateTrack { pattern :: Pattern String, channel :: Int }
  | CVTrack   { pattern :: Pattern String, bus :: Int }
```

Tick handler dispatches: gate tracks fire MIDI + `/tidal/gate/trig`
(with optional V/oct pre-set via `sampleCVMap`); CV tracks parse tokens
as `Number` and emit `/cv` updates on their bus. New scheduler
messages `UpdateGateTrack` / `UpdateCVTrack` replace the matching track
by channel/bus, leaving others untouched — proper live-coding shape.

Independent cycle lengths between tracks compose naturally (Tidal's
`queryArc` is pattern-relative). Demonstrated with `gate 0 bd*4` +
`cv 11 0.0 0.2 0.4 0.6 0.8` running side-by-side: 4-event kick pattern
gets pitch-modulated by 5-event CV pattern within one cycle.

**OSC robustness — per-send socket**:

Twice today the BEAM's long-lived OSC `gen_udp` port silently stopped
delivering after cv-router restarts (no error, no socket close —
packets just don't arrive at the new cv-router PID). Symptom: scheduler
logs `⚡ bd → gate 0 in 70ms` correctly, gen_udp:send returns `ok`,
cv-router log shows nothing.

Fix: `sendGateTrigAfter` / `sendCVAfter` open a fresh UDP socket per
send instead of reusing the Client's stored socket. `gen_udp:open(0)`
is microseconds; sleep is *before* open, so fd lifetime is ~tens of µs
per send. At musical event rates (4-32 events/sec) fd pressure is
negligible. If we ever need >1kHz sustained CV (banks of LFOs), the
right fix is a dedicated long-lived OSC sender process that re-opens
on send-failure — note for later.

### Audible result

`gate 0 bd*4` + `cv 11 0.0 0.2 0.4 0.6` — 4 kicks per cycle through
Rample 1, each at a different pitch (CV patched to Rample 1's pitch
input in this test). Confirmed working end-to-end at musical timing.

## Decisions

- **Per-send UDP sockets, not a long-lived sender process** — for now.
  Simpler, same-day. Switch to dedicated sender if event rate climbs.
- **Mute DSP 1 entirely** — the factory `Input 9-14 + S/PDIF → Out 1-8`
  passthrough was summing onto our cv-router outputs. Andrew doesn't
  use ES-3 expander or S/PDIF in the current rig.
- **Use `Bus 1` as the neutral source for muted slots** — keeps the
  Electron mixer view unambiguous (no doppelgänger USB labels).
- **Default save-to-flash slot is `1` (Hosted)** — matches the workflow
  where ES-9 boots into Hosted mode under USB. Prior accidental writes
  to slot 0 (Standalone) didn't actually load on power-cycle.
