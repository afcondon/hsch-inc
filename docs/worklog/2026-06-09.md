- **Tier-2 eDSL, increment 1** — `examples/numexpr-edsl/Data.NumExpr`
  (commit `931aa61`). A numeric-expression precision ADT with `Ring`/`Semiring`
  instances (`num 10.0 * (var "y" - var "x") + sinE (var "z")`). The expression
  crosses the seam **once**: `toJExpr` folds the AST through handed-in Julia
  builders (ADR-0002, constructors across — the shim never destructures a PS
  ADT), then Julia metaprograms it into a native function via `eval` of a
  generated lambda. A pure PS interpreter gives the reference semantics; the
  Julia-compiled function matches **byte-for-byte** (`staging faithful: true`).
  This is the real answer to the `mapNum` callback anti-pattern — structure
  crosses once and compiles, not a closure per element.

- **Tier-2 eDSL, increment 2** — `Data.SystemSpec` (commit `ef7198e`). A
  **row-typed** system of ODEs: state space and params are PureScript rows, RHS
  written with typed field access (`s.x`, `p.sigma`; a misspelt `s.q` is a
  compile error). RowList machinery: `MakeVars` builds the variable records,
  `CollectEqs` reads the equation record in order, `Keys`/`ToValues` handle
  labels/values, `NumberRow` ties `Number`-valued ICs/params to the system's
  `NumExpr` rows so they're type-checked yet carry numbers. The vector field is
  compiled to native Julia and integrated by a native RK4 loop; the **Lorenz**
  system reproduces the independent `lorenz-leaf` RK4 (**maxZ ≈ 47.834**). The
  "Native" evidence-category keystone (Marginalia 220), realised.

- ADR-0007 carries dated progress addenda for both increments (`025a0e2`,
  `a10fe7f`); it stays **Proposed** pending the MTK denotation and the items
  below.

- **Tier-2 eDSL, increment 3** — `Data.MTKSystem` (commits `ce210d1`,
  `9e5a424`). Denote the *same* row-typed `SystemSpec` into **ModelingToolkit**
  instead of the hand-rolled RK4. The seam is unchanged: PS hands the ordered
  var names + one RHS `JExpr` per equation across (increment-1 currency); Julia
  binds them to Symbolics variables, evaluates the Exprs into a symbolic
  `System`, `mtkcompile`s it, derives the **analytic Jacobian**, and solves with
  SciML's default auto-stiff adaptive polyalgorithm. The MTK-solved Lorenz
  matches the RK4 / `lorenz-leaf` envelope (maxZ 47.69 vs 47.83 — chaotic, so
  envelope-agreeing not bit-identical), and a genuinely **stiff** Robertson
  system is solved cleanly (mass conserved Σy = 1.0) — something fixed-step RK4
  can't do. The printed analytic Jacobians (Lorenz and Robertson) are the demo's
  visible payoff: derivatives PureScript never wrote. First non-stdlib Julia
  dependency — a dedicated `examples/numexpr-edsl/julia-env/` (MTK v11), with
  `Project.toml` + compat committed and `Manifest.toml` gitignored.

- **RGF cleanup — ADR-0007 now Accepted** (commits `bcb1c66`, `49c6b7f`).
  `Data.NumExpr` and `Data.SystemSpec` compile their staged lambdas with
  `@RuntimeGeneratedFunction` instead of `Base.eval` + `Base.invokelatest`: the
  RHS functions are native, specialize, and are callable in the current world
  age, so the per-call `invokelatest` is gone from the NumExpr batch eval and the
  SystemSpec RK4 inner loop. Byte-identical results. RGF added to `julia-env` (a
  lightweight transitive dep, now direct); all three increments share that env.
  With this, the "descriptions across, handles back" doctrine is realised with no
  interpreter/world-age glue on any tier → ADR-0007 flipped Proposed → Accepted.

- **The MTK v11 API differs substantially from older docs** and every
  version-sensitive line was validated with a standalone `/tmp/mtk_probe.jl`
  before touching the FFI: `System` (not `ODESystem`) with explicit
  unknowns/params; `mtkcompile` (not `structural_simplify`); state variables via
  the `@variables x(t)` macro (the functional `variable(; T=FnType)` path is
  gone); `ODEProblem` takes a single merged operating-point map; and
  `mtkcompile` **reorders the unknowns**, so results are read back by *symbolic
  index* (`sol[var]`), never positionally — the bug that first showed up as a
  wrong maxZ (19.5 instead of 47.7).

- **Tier-2 eDSL, increment 4 — DAEs + a Hylograph frontend.** `Data.DAESystem`
  extends the row-typed surface from ODEs to **differential-algebraic** systems:
  a third `alg` row of algebraic variables (no time derivative) plus one closing
  constraint per algebraic variable — the constraint lambda returns a `Record
  alg`, so the type pins exactly one constraint per variable (a well-posed
  index-1 DAE by construction). Demo: a **double pendulum** in Cartesian
  coordinates. The FFI denotes it into MTK (state + algebraic vars are functions
  of `t`, params not), `mtkcompile`s an index-1 DAE keeping the two rod tensions
  as algebraic unknowns, and **`Rodas5P`** (implicit stiff) holds the rigidity
  constraints by Newton iteration every step — rod drift **~2.8e-8** through 20s
  of fully chaotic motion (the drift is computed back in PureScript from sampled
  positions). `scipy.solve_ivp` can't do this (no DAE/algebraic-variable
  support); the WASM backend has neither a symbolic stack nor an implicit solver
  — this is the "you couldn't just do it in Python" demo Andrew wanted. End-to-end
  through the full PS→purejl→Julia pipeline, 1200 frames written to JSON.

- **Numerics gotcha — coordinate singularity, validated by probe before any
  eDSL code.** Full *automatic* index reduction of the Cartesian pendulum (MTK's
  default `mtkcompile` to an ODE) divides by a chosen coordinate and blows up
  exactly when a rod is vertical (confirmed: `Unstable` at `x=0.0, y=-1.0`, t≈0.59
  — even `Rodas5P`). The robust formulation writes the constraint at the
  *acceleration level* (`0 ~ u²+v²+T(x²+y²)−gy`), which keeps the tension as a
  nonsingular algebraic unknown (divides by `Lᵢ²≠0`); MTK keeps it as an index-1
  DAE and `Rodas5P` solves it cleanly through the singular configuration. Standard
  multibody practice. All of this was nailed down in throwaway `/tmp` probes
  before touching the eDSL — same discipline as the MTK-v11 API validation.

- **Hylograph frontend — `examples/numexpr-edsl/viz`.** A standalone Hylograph
  (HATS) Halogen app — its **own** spago workspace (registry set `77.5.0`, JS
  backend), independent of the purejl build, coupled to the backend only by
  `double-pendulum.json`. A pure *player*: per ~16ms tick it advances a frame
  index and re-renders rods/joints/bob-2 trail as a declarative SVG tree
  (`HATS.elem` composed with `<>`, `rerender` into a container; Halogen owns only
  a static host div). Validated by headless-Chrome screenshot with a virtual-time
  budget — the chaotic red trail renders correctly. The cross-runtime thesis made
  visible: one typed description, Julia computes, PureScript/JS draws.

- **Chose the demo deliberately for un-dismissability.** Andrew's framing: avoid
  a demo where someone shrugs "I could've done that in Python/WASM." Lorenz fails
  that test (we've shipped a WASM Lorenz; scipy does stiff ODEs). A high-index DAE
  requiring automatic constraint handling is the discriminator — `scipy.solve_ivp`
  literally can't take the model as input. (The "three ways to compute Lorenz"
  triptych remains a nice *secondary* polyglot-site piece — it invites the shrug,
  and the pendulum sitting beside it is the rebuttal.)

## Decisions Made

- **Single-lambda `system` over a record-of-lambdas.** `system \s p -> { x: …,
  … }` instead of `{ x: \s p -> …, … }`: the former pins `s :: Record state`
  and `p :: Record params` from `system`'s signature, so the lambda field types
  resolve; the latter left the args as open rows and instance resolution
  failed. Also nicer ergonomically.
- **`NumberRow` to separate the eDSL row from the value row.** The system's
  state row is `NumExpr`-valued (for var records); ICs/params must be
  `Number`-valued with the same labels. `NumberRow` derives the Number row from
  the NumExpr RowList, keeping ICs type-checked against the system.
- **`record` shims kept per-example for now.** `Record.Builder` /
  `Record.Unsafe.Union` mirrored from the real JS foreigns into the example's
  `ffi-jl/`. Common enough to promote to built-in `purejl` shims — deferred (a
  Foreigns.hs change + stack rebuild).
- v1 uses Julia `eval` + `Base.invokelatest` at the call boundary; the
  expression bodies and RK4 arithmetic are native. RuntimeGeneratedFunctions
  would drop the `invokelatest` — noted in the shim and ADR-0007.
