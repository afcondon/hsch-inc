# 2026-07-28 — Publishing the graph JSON contract, and paying down the Internal namespace

Continuation of the previous day's `hylograph-graph-json` work. Two
threads: getting the format into Paul's hands, and fixing the two
ecosystem defects that building it exposed.

## Accomplished

**`purescript-hylograph-graph-json` pushed public.**
<https://github.com/afcondon/purescript-hylograph-graph-json> — 20 files,
MIT licensed, README fronted with an "If you are writing an emitter"
section. Deliberately *not* published to the registry.

**Three libraries released.**

| Package | Version | What |
|---------|---------|------|
| `hylograph-selection` | 0.5.2 | Public vocabulary out of `Internal`, plus HATS re-exports |
| `hylograph-simulation` | 0.6.0 | Four dead types removed |
| `hylograph-simulation-halogen` | 0.5.1 | Dependency bound widened (cascade point) |

**Five vocabulary modules promoted out of `Hylograph.Internal`**, old paths

**Afternoon: two anomalies the CI survey exposed, both closed.**

`hylograph-components` — seventeen working chart modules (BarChart,

git repository at all**, while a *public* repo depended on them by relative
path. Now at
<https://github.com/afcondon/purescript-hylograph-components>, with the

`purescript-hylograph-demos` **did not build for anyone**, including here.
`purescript-jtms` had become `purescript-baskerville` and this repo was
never told, so three `path:` dependencies pointed at directories that do
not exist. Repointed at `baskerville-core` / `baskerville-sudoku`,
`jtms-testkit` dropped (no counterpart, nothing used it), and the module
namespace followed — `Jtms.*` → `Baskerville.*` across two demo packages
and a test suite. Then the directories, package names, Makefile list, site
links, thumbnail and CSS class renamed to match; two published URLs change
as a result. The `components/` demo was committed too — also untracked
source.

## Decisions Made

- **Ship the repo, defer the registry.** Paul's producer is C++; it
  consumes the format, the example files and the checker, none of which
  need a registry release. Publishing is a *stability promise*, so making
  it for a shape no emitter has exercised is backwards. A GitHub repo
  unblocks him today; 0.1.0 can mean something later.
- **Patch bump for the `Internal` move (0.5.2), minor for the deletion
  (0.6.0).** Shims preserve the exact public surface, so promotion is
  purely additive and needed no downstream coordination. Removing exports
  is breaking by the letter of semver even with zero importers, because
  neither the registry nor any consumer can verify that claim.
- **No `extraPackages` override** to force `hylograph-selection` 0.5.2 into
  the worked example. It would trade a visible two-line comment for an
  invisible obligation to remember to remove it — the exact debt pattern
  this whole thread has been digging out of.
- **Path-scoped commits throughout.** Every repo touched had unrelated work
  in flight; `hypo-punter` alone had thirteen modified files including its
  own `landing/spago.yaml`. Nothing got swept up.
- **Uppercase `JTMS` deliberately not renamed** in three places describing
  Make's semantics as "monotone JTMS rules". Baskerville *is* a
  justification-based truth maintenance system; those sentences are about
  the concept, not the package. A blind search-and-replace would have
  turned correct terminology into a false claim.
- **The components demo committed but not wired in.** It is absent from the
  Makefile `DEMOS` list and unlinked from the site. Source first, because
  that was the part at risk; publishing a new demo page is a deliberate act,
  not a side effect of committing.

## Findings

**The diagnosis was wrong, and the truth was better.** The `Internal`
modules' headers had been saying *"use the public API in
`Hylograph.Behavior`"* — and `Hylograph.Behavior` was never written. Nor
`Hylograph.Transition`, nor `Hylograph.Selection`. The code was correctly
marked internal, the docs correctly redirected the reader, and the
destination did not exist. Those ~470 imports were not a boundary being
ignored; they were the only door in the building.

Generalising: a *misplaced* boundary and an *unfinished* boundary look
identical from outside — both present as consumers reaching into
`Internal` — and want opposite responses. Reading the module header
distinguished them, and took thirty seconds.

**Publishing does not make a version reachable.** Package sets pin versions
and *override* dependency ranges. Set 77.13.1 pins
`hylograph-selection: 0.5.1`, and so does the newest published set,
80.0.0. So the range widening across seven repos was necessary but not
sufficient — it prevents a conflict when the set advances, it does not
advance anything. The visible consequence is that the worked example still
imports `Internal` despite the fix being live.

**Two libraries were declaring `license: MIT` with no licence text**, five
releases each. Files added before publishing rather than making it a sixth.

**Relative paths are silently relative to something, and nothing records
what.** Three variants of the same hazard in one afternoon: a renamed repo
that could not warn its dependents; a `path:` dependency on a directory in
no repository; and a Makefile rule doing `cd $demo && spago bundle`, where
relative `path:` entries resolve against the *working directory* — so the
two demos with sibling-checkout dependencies could not be built by `make`
from anywhere. All three are the unidirectional-reference problem
(§6b of `plans/minard-for-operations.md`) wearing different hats.

**A commit can lie about itself.** The first rename commit moved the
directories but omitted the edits inside the moved files — `git status`
showed `RM`, which is renamed-in-index *plus modified-in-worktree*, and I
read the pair as both staged. The message described changes the commit did
not contain. Fixed in a follow-up; worth remembering that `R` and `RM` are
materially different.

**`simulation-halogen` was a hidden cascade point.** Published, and
depending on `hylograph-simulation <0.6.0`, so anyone wanting both would
have been stuck. Widening its bound required its own release to mean
anything — the sort of thing that is invisible until you enumerate the
dependency graph.

## Findings (afternoon)

**A green build can mean nothing was built.** Those nine errors had been
there for some time, unnoticed, because *spago does not re-report warnings
for modules it does not recompile*. `spago build` on a warm `output/`
prints `Errors 0` and exits zero on code that fails a clean build. CI that
caches `output/` inherits exactly this. Noted in `plans/hylograph-libs-ci.md`.

**The recorded survey was wrong in a way that mattered.** "18 + 6 + 2
imports" was a count of grep hits, not of consumers. Real external demand
is 11 names, and the three modules turn out to have three different
problems, not one:

- `Internal.Transition.FFI` — zero external importers. Its two hits were
  internal. Needed nothing.
- `Internal.Behavior.FFI` — a genuine missing-API leak. This is what 0.5.3
  fixes.
- `Internal.FFI` — not a leak at all. The four arc-generator sites are
  pinned at `hylograph-selection: 0.1.1` and import `arcGenerator_`, which
  the library **deleted**; `Internal/Generators/` is now an empty
  directory. No wrapper helps them.

Generalising: a grep count over a monorepo tree measures neither consumers
nor severity, and `.spago/` caches inflate it. Three of those hits were
copies of the library's own source.

**Version keys do not sort as strings.** Chasing a resolution failure I read
`sorted(published)[-3:]` on registry metadata and concluded `parsing` had
no 11.0.0, when `'9.1.0' > '11.0.0'` lexicographically. Wasted a diagnosis
and produced a spurious edit before the real cause appeared: the registry
metadata was simply still settling. The `compilers` array for a fresh
publish fills in as the matrix jobs run, and spago fails with the
unhelpful "Didn't find version in the metadata file" until it has. Waiting
a few minutes was the whole fix.

**Publishing still does not make a version reachable.** Set 77.13.1 pins
0.5.1 and package sets override declared ranges, so `>=0.5.1 <0.6.0`
resolves to 0.5.1 regardless. `hylograph-demos` needed an explicit
`extraPackages: hylograph-selection: "0.5.3"` — the documented mechanism,
carrying a comment saying when to remove it.

# Evening session — application-aware disk inventory, and a Mac Mini off the tailnet

A different thread entirely: not PureScript work, but part of the
**stateless-laptop** effort. Started as "what if `du` bucketed by
application instead of directory?" and turned into a small tool, ~43 GB
reclaimed, and an unrelated Tailscale fault found on the way.

## Accomplished

**`purser` — built, at `~/work/afc-work/purser`.** Zero dependencies,
stdlib Python, four commands:

| Command | What |
|---------|------|
| `scan` | one filesystem walk → `index.jsonl` (~2 min, 3.4M files) |
| `apps` | usage by *application*, not directory — the headline view |
| `verify` | is code classified "reproducible" actually pushed? |
| `report` | recoverability buckets per `rules.toml` |

Scan and report are deliberately separate passes. The walk is the slow,
boring artifact; the rules are what actually gets iterated on, and
splitting them means rewriting rules costs nothing.

**207 applications identified with almost no hand-written rules.**
`/Applications` says what exists, each `Info.plist` gives the bundle ID,
and macOS convention puts that app's state under that identifier across
`~/Library/{Application Support,Caches,Containers,Group Containers,…}`.
Three fallbacks cover the rest: team-ID prefixes for group containers
(`2BUA8C4S2C.com.agilebits`), vendor-name matching (apps name the folder
`Ableton`, not `Ableton Live 11 Suite`), and a short alias list for
genuinely unconventional locations. Vendor keys are used only when they
resolve to exactly one app, so `apple` and `google` are dropped as
ambiguous rather than swallowing half the disk.

Ableton reads 12.0 G across six places against a 5.3 G app bundle. The
tool beat manual inspection — a by-hand count found 10.3 G and missed
1.8 G of caches.

**~43 GB reclaimed.**

- **42 GB of iOS device backups** — iPhone XR and iPhone 11, last backed
  up 2026-04-14 and 2026-03-22. Not backups in any useful sense: restore
  points for phone states that no longer exist.
- **866 MB of PostgreSQL 15**, an EnterpriseDB artifact from Jan 2023,
  `data/` untouched since 3 Apr 2023, no `~/.psql_history`, zero shell
  history for `psql`/`createdb`/`pg_dump`, no connection strings in any
  project. Neither Marginalia nor infovore-larder-db use it (the latter is
  SQLite). 70% of that install was pgAdmin, never launched.

**Mac Mini restored to the tailnet.** Three stacked faults: the App Store
Tailscale build runs as a *user agent*, so a Mini that boots to the login
window after a power cut never rejoins; MagicDNS kept answering
`andrews-mac-mini` with the dead node's address, so it presented as a DNS
problem while DNS worked perfectly; and reinstalling minted a *new* node
(`andrews-mac-mini-1`) because deleting the app took its keys, leaving the
old name bound to a corpse. Fixed by the standalone (`macsys`) build,
which ships a network extension, plus deleting the stale node and renaming.
Verified across a reboot with nobody logged in — 9.7 ms direct, all ports up.

**Marginalia #265** — "Large-format print workflow"
(`juliet-echo-charlie-delta`), `infrastructure/photography`, status
`someday`, related to #5 Infovore Data Sources.

## Decisions Made

**Classify by recoverability, not size.** For a stateless machine the
question is "what exists only here?", so `rules.toml` sorts into
`derived` / `reproducible` / `cloud` / `precious`, and the *unclassified*
remainder is the headline rather than a footnote. Currently 50 GB (8.7%).

**"Reproducible" is a claim about the network, not the filesystem.** No
path-matching rule can check it, hence `verify`: for each repo, does HEAD
exist on a remote, is the tree clean, is anything stashed. 90 of 205 repos
fail — 65.6 GB currently sitting in a bucket labelled "safe to lose". The
`.spago`/`node_modules` checkouts are skipped as vendored; they were 999
of 1204 "repos" before filtering.

**Kept the Topaz apps rather than deleting them.** 9.2 GB unused for 2–3
years, but a Topaz perpetual licence only covers versions released inside
the ownership window and their download page foregrounds current releases.
The entitlement is account-side (auth tokens on disk are empty), so the
risk is *availability of these builds*, not loss of licence. 4.5 GB of
Photo AI's 5.1 GB is `Contents/Resources/models`, so the bundle is
self-contained and a copy is a working artifact. Being copied to the Mini,
where they'd be used anyway.

**Left Time Machine alone.** It measured 77.6 GB and looked like the
second-largest consumer on the machine. It isn't: **APFS snapshots are
sized by churn, not by what you store.** A snapshot costs nothing at
creation and grows only as blocks change or are deleted, so the 77.6 GB
was mostly that afternoon's own 42 GB deletion passing through. Real
steady-state churn is 9.1 GB/24h. Clearing large static directories would
have done nothing, and deleting things briefly makes it *worse*.

**Removed the PostgreSQL rule rather than fixing it.** It classified
`/Library/PostgreSQL` as precious "live database state" from the directory
name alone, and was wrong. Replaced with a comment, because the durable
lesson is that a path-matching rule cannot answer "is this database live?"

## Findings

**The uninstaller lied by omission.** EnterpriseDB's uninstaller reported
leaving `data/` and the `postgres` account — but *silently* also left
`/Library/LaunchDaemons/postgresql-15.plist`, by then pointing at a
`postmaster` binary it had just deleted. A `RunAtLoad` daemon failing at
every boot. Three manual steps finished the job; Apple's own `_postgres`
user and group were left alone (the underscore distinguishes them from
EnterpriseDB's unprefixed `postgres` at uid 502).

**Screen Sharing worked throughout while Finder's Connect As failed, from
the same pane.** Both Bonjour records point at `Andrews-Mac-mini.local`
(`_rfb._tcp:5900`, `_smb._tcp:445`). Screen Sharing uses the resolved
Bonjour endpoint directly; the SMB path re-derives the address from the
hostname, which hits `search domain[0] = vaquita-paradise.ts.net` and gets
the dead tailnet IP. Two buttons, one pane, no shared code path.

**Size is the weaker half of the question.** Adding `mtime` made both
deletions obvious in a way size never did — the iOS backups looked like
ordinary usage until their dates showed. `--cold` needs a size floor
(default 100 MB) or age alone puts 24 KB of Automator above 5 GB of
abandoned Topaz.

## Session close

Topaz resolved, and the premise that made it interesting turned out to be
false. The Topaz account page reported the licence as "expired", but
downloading and re-activating on the Mac Mini worked — **"expired" gates the
upgrade window only**, not downloads of entitled versions and not use. The
apps were redownloadable all along, so the 9.2 GB was deleted outright rather
than preserved.

The durable finding is about copying, not licensing. Both Topaz bundles fail
`codesign --verify` on *any* machine, because Topaz writes AI models into the
signed bundle post-install ("a sealed resource is missing or invalid"). That
is invisible locally — macOS does not re-validate an app it has already
launched — but a copied bundle is new to its destination and faces
first-launch assessment. Gigapixel survived it; Photo AI was refused as
"damaged". The fix was never to repair the copy: use the vendor installer.
Copying macOS app bundles between machines is a worse idea than it looks.

Two mechanical notes worth keeping. Deleting an app from `/Applications`
needs **App Management** permission, which a shell does not have — `rm`
fails with `Permission denied` regardless of ownership, and Finder is the
correct tool. That failed `rm` had already removed ~4.5 GB of writable model
files before hitting the block, leaving a 629 MB / 910-file remnant rather
than an intact bundle. And the Mac Mini's login is `andrew`, not `afc`.
