# 2026-05-21 — purerl-tidal vmod timing investigation

Epic session. Started from yesterday's Phase 4 measurement (15 ms IOI
stdev on the René vmod vs 0.03 ms on Tidal patterns — same audio
chain, two orders of magnitude worse) and root-caused it through to a
four-fix sequence that brings vmod audio jitter to within 7× of the
Tidal-pattern reference and validates multi-voice scaling.

## Accomplished

**Four timing fixes for the vmod emit path** — all four landed on
`rene_voice`, `grids_voice`, `repetitor_voice`:

1. **F1 — Cache the live-control ControlMap across ticks.** Added a
   monotonic version counter to `tidal_control_bus`; threaded
   `controlVersion` through the `Window` broadcast in `tidal_clock`;
   each voice caches the opaque PureScript `ControlMap` keyed by
   version and rebuilds only when it changes. Each vmod's PureScript
   surface (`Tidal.Rene`, `Tidal.Grids`, `Tidal.Repetitor`) now
   exports `buildControlMap` and `evaluateParamsAtControls`. Real
   win at the BEAM-step level (eval mean 2.18 → 1.36 ms, max 14.94 →
   6.98 ms) but did not move audio jitter on its own — F1 alone
   stayed at 17 ms IOI stdev.

2. **F-LAT — Device latency compensation.** Tidal's `Dispatcher.purs`
   subtracts `dev.latencyMs * 1000` from `wallUs` before
   `scheduleNoteAt`; the vmod path skipped it. Walker now accumulates
   a `device_latencies` map keyed by alias from `registerMidiDevice`
   events and passes `latency_ms` into VoiceConfig. Voice stores
   `latency_us` and subtracts in `emit_step`.

3. **F-FUTURE — Discover one step ahead.** The load-bearing fix.
   `process_window` was using
   `EndStepExcl = trunc(LookAhead * StepsPerCycle)` to decide which
   steps to emit; step S only became visible once
   `la * sp ≥ S + 1`, by which time `currentCycle` had already passed
   `S/sp` and **WallUs landed ~150 ms in the past on every step**.
   link-spike / CoreMIDI fired ASAP, Live block-quantised, audio
   scattered.  Tidal-pattern path doesn't have this problem because
   it queries by integer-cycle window and clamps `delayClamped =
   max 0.0 delayMs`.  The vmod port inherited neither safety net.
   Fix: `+1` to `EndStepExcl`. WallUs now lands 18-70 ms in the
   future (0 events scheduled in the past, vs 100% before).  IOI
   stdev dropped 17 → 0.17 ms (~100×).

4. **F-LEAD — Bump `lookAheadMs` 100 → 300 ms.** F1+F-LAT+F-FUTURE
   produced clean 60 BPM audio but 120 BPM × 16 stepsPerCycle still
   had audible glitches every ~10 s. Cause: step interval (125 ms) >
   old lookAhead (100 ms), so minimum lead time approached zero on
   adverse tick alignments. At 300 ms the minimum is ≥175 ms.
   Result: max excursion 15.88 → 5.37 ms; audible-glitch artifact
   eliminated. Tidal-pattern path queries by integer-cycle window so
   it's invariant under this change.

**F4 — Tried and reverted.** Hypothesised that `erlang:garbage_collect()`
at end of each `compute_until` cast would clear the heap between
ticks and pre-empt the multi-ms BEAM tail spikes. In practice didn't
help and arguably slightly hurt on small samples. BEAM tail spikes
do exist but sit comfortably inside the F-LEAD lead-time cushion.
Reverted within minutes of landing.

**Phase 5 multi-voice scaling validated.** Two identically-configured
Grids voices on iac ch10/11, panned hard L/R into a single stereo
recording. Wrote `tools/timing-analysis/analyse_stereo.py` — detects
onsets per channel, pair-matches within tolerance, computes
inter-voice offset directly. Result: median offset **+0.03 ms**
(sub-sample at 48 kHz), p95 = 2.5 ms, max = 18.55 ms across 2,100
matched pairs. Audibly lockstep. 1% tail is BEAM scheduler
unfairness on individual ticks — rare enough to be inaudible in
performance. Multi-voice scaling closed.

**Anchor-log ghost trap.** One unreproducible test run showed both
voices dropping ~8 bars worth of audio in lockstep during the first
22 s, then settling. Couldn't reproduce. Built `tidal_anchor_log`
ring-buffer (capped at 2,048 entries, ~µs/write) with four event
kinds:

- `anchor_rx` — every `/link/anchor` packet receipt
- `clock_transition` — every free-running ↔ anchored boundary cross
- `voice_dropout` — `EndStepExcl ≤ StartStep` silent skip
- `voice_step_burst` — `EndStepExcl - StartStep > 8` (forward jump)

WS verbs `dump-anchor-log` (CSV) and `clear-anchor-log` to retrieve
and wipe. Always-on, low-cost, waiting for the next instance.

**Documentation:** Full root-cause write-up at

Memory entries `reference_vmod_audio_timing_fixes.md` and

## Explored but not pursued

- **F4 explicit GC.** Implemented, measured, reverted within an hour.
  Notable finding: BEAM tail spikes are absorbed by F-LEAD's
  lead-time cushion; no need to fight GC directly.
- **Root-causing the startup-dropout phenomenon.** Hypothesis is the
  documented "phase-jump on Link anchor arrival" in
  `tidal_link_anchor:scheduler_clock`, but couldn't reproduce without
  the specific conditions of that one run. Switched strategy to
  always-on instrumentation that traps it next time.
- **Forcing voices to wait for `synced=true` before emitting.**
  Considered as a clean fix for startup dropouts. Andrew's
  instinct: it's a smell that Link falls off at all, and ameliorating
  might mask a deeper problem. Trap-and-wait approach instead.

## Decisions made

- **Keep the PureScript vmod architecture.** Started the day asking
  whether vmods need to be rewritten in Erlang for performance.
  Answer: the chain CAN be tight; the implementation just had three
  separate compounding issues that all looked superficially fine in
  isolation. Vmod path now indistinguishable from Tidal-pattern path
  at the audio chain.
- **Always-on diagnostic instrumentation over reactive debugging.**
  When the startup-dropout phenomenon didn't reproduce, building the
  ghost trap was a better investment than speculative root-causing.
- **Marginalia summary now reflects "vmod timing is settled".** The
  substrate work is the active surface; the BEAM runtime is no
  longer a question.

## Parking lot

- **F2 — Pre-resolve static `pure value` Patterns at registration
  time.** Walker grows a `static_pattern?` predicate; voice receives
  flat Erlang arrays for static slots, skips FFI for those. Estimated
  -2 ms off eval_FFI for common configs. Bigger surgery than F1;
  queued, not blocking performance.
- **F3 — `erlang:send_after`-based emit instead of timestamp gambit.**
  Voice holds events and fires them at the right wall time directly.
  Removes the dependency on link-spike/CoreMIDI's timestamp scheduling.
  Probably not needed given current numbers.
- **Inspecting the case_clause crashes in the log.** Pre-existing from
  17-May, unrelated to today's work. Worth a separate session.
- **Per-step instrumentation for grids/repetitor.** Currently only
  rene_voice has the `samples` field + `dump-rene-samples` /
  `clear-rene-samples` WS verbs. Generalising to all vmods would
  give us per-voice phase-cost data without needing to bring up a
  rene voice for diagnosis.
